Gap Analysis · SEVO / CalServices · Customer + Vendor

What separates SEVO from NoBroker and Porter

A file-level audit of the two shipped codebases against the workflows that mature home-services and on-demand-logistics marketplaces actually run. The engineering already built is substantial — a 9-gate dispatch engine, a geofenced arrival check, a COD-with-OTP payment state machine, a work-extension approval loop. The gaps are mostly at the seams: the two applications share a database but not a contract, and the parts that would make a customer trust the platform — real payments, real notifications, real tracking — are stubbed.

The single most important structural fact

The two applications are joined only by shared database tables and a 5-second polling loop. The HTTP integration that both sides appear to implement does not connect: the customer app calls endpoints the vendor app does not route, using an authentication scheme the vendor app does not accept, and the vendor app never calls the customer app's webhook receiver at all.

Almost every "real-time" gap in Parts 2 and 3 is a downstream symptom of this one fact.

Part 1

Platform seams

Eleven gaps that are not specific to either service category. They sit between the two applications, and they cap how good either category can get. Fixing these first makes every later fix cheaper; fixing them later means re-doing work.

X-01
The vendor app never tells the customer app anything
P0
What's missing

The customer app has a fully built webhook receiver that understands fifteen events — technician assigned, accepted, on the way, arrived, service started, completed, location updated, payment collected, extension requested, proof submitted, rescheduled and more. It has signature verification, replay protection and an idempotency table. The vendor app emits none of them. It contains no outbound HTTP calls whatsoever.

Why it matters

Everything the technician does is invisible to the customer except what can be inferred from a shared status column. No "your technician has accepted", no live position, no arrival alert, no payment confirmation. From the customer's seat the booking goes quiet after confirmation and reappears when someone knocks on the door.

How mature platforms do it

The partner app is the source of truth for field events and publishes each one exactly once to the consumer platform — typically an event bus, or an outbound webhook with retry and an idempotency key. The consumer app never polls for state it should have been told about.

What to change
  • Vendor Add vendor/backend/workforce_api/services/marketplace_events.py — an emitter that POSTs to {CUSTOMER_API}/api/workforce-integration/webhook/ with the HMAC header the receiver already expects, an incrementing sequence, and a persisted outbox row for retry.
  • Vendor Call it from every state-changing view in workforce_api/views.py (offer accepted, arrive, OTP verified, proof, cash collect) and from services/automatic_dispatch.py after WorkforceJobOffer creation and acceptance.
  • Vendor Emit technician.location_updated from WorkforceLocationUpdateView, throttled to one event per 10–15 s per active job.
  • Customer No change — the receiver in workforce_integration/views.py already handles all fifteen types.

Evidence: Customer/backend/workforce_integration/views.py:154–397 (handlers) · vendor/backend/ contains no requests.post to any marketplace host.

X-02
The customer app's outbound integration client calls endpoints that do not exist
P0
What's missing

WorkforceIntegrationService calls /jobs/dispatch/, /technicians/<id>/feedback/, /customer/quote-token/<token>/ and /tracking/<id>/. None of these are routed by the vendor app. The two that are close to real (/jobs/<pk>/live-tracking/) are called with a string request ID like AC0012 against an <int:pk> route, and authenticated with a static bearer key while the vendor app's default permission class is IsAuthenticated over JWT. Every call fails.

Why it matters

Two consequences. First, every feature built on this client silently degrades to a fallback: the customer quote page can never load, feedback never reaches a technician's profile, live telemetry never enriches the tracking payload. Second — and this one costs money — dispatch_job() runs synchronously inside the booking POST with a 5-second timeout, so every single booking request blocks for up to five seconds waiting for a 404.

How mature platforms do it

A cross-service call in the request path is either removed or made asynchronous. Booking creation returns as soon as the order is durable; matching happens on a queue. Service-to-service auth is a real machine credential the callee actually validates.

What to change
  • Both Write the integration contract down once (OpenAPI or a shared markdown spec) and generate both sides from it. Today each side implements a different imagined contract.
  • Customer service_requests/views.py:409 — move WorkforceIntegrationService.dispatch_job(sr.id) out of BookingCreateView into a Celery task. Celery is already installed and configured.
  • Vendor Add a service-account authentication class in vendor/backend/accounts/authentication.py that accepts the shared WORKFORCE_API_KEY, and route the four missing endpoints in workforce_api/urls.py.
  • Customer Remove the silent except Exception → fallback: True swallowing in workforce_integration/services.py; a failed integration call must be visible in monitoring, not reported as success.

Evidence: Customer/backend/workforce_integration/services.py:95, 217–219, 283, 298 vs vendor/backend/workforce_api/urls.py · vendor/backend/workforce_core/settings.py:158–165.

X-03
Two different state machines write to the same status column
P0
What's missing

Both applications define a ServiceRequest.Status enum and an ALLOWED_TRANSITIONS map over the same status column — and they disagree. The vendor app writes offering, dispatching, redispatching, reassigned, en_route and service_started, none of which exist in the customer app's enum. The customer app writes waiting_for_payment, reviewed, awaiting_verification, verified, feedback_pending, feedback_received, closed, rejected, rescheduled and rework_requested, none of which exist in the vendor's transition map.

Why it matters

A booking the vendor app has moved to offering renders in the customer UI as an unrecognised status; the customer's own state machine will refuse the next legal transition because the current state isn't a key in its map. A booking the customer app has moved to rework_requested disappears from the vendor's dispatchable set. This is the class of bug that produces "stuck bookings" that only an engineer with database access can clear.

How mature platforms do it

One order lifecycle, owned by one service, with a single enum published as a shared artifact. Other services propose transitions through an API; they do not write the column directly. Anything that needs a private sub-state keeps it in its own table.

What to change
  • Both Publish one canonical status enum and transition graph as a shared module vendored into both repos. The union of both current maps is the starting point.
  • Vendor Move dispatch-internal states (offering, dispatching, redispatching) off ServiceRequest.status and onto WorkforceJobOffer.status, where they belong — the offer table already models exactly this.
  • Both Add a CI check that fails the build if the two enums diverge.

Evidence: Customer/backend/service_requests/state_machine.py:16–44 vs vendor/backend/service_requests/state_machine.py:11–33.

X-04
The shared table's schema has drifted between the two ORM definitions
P0
What's missing

The customer app owns the migrations for service_requests_servicerequest. Migration 0038 dropped the assigned_employee foreign key. The vendor app's unmanaged model still declares it and its entire dispatch engine filters on it (assigned_employee__isnull=True, assigned_employee=emp). Separately, latitude/longitude are DecimalField(9,6) on the customer side and FloatField on the vendor side; and the vendor model has no tracking_token, otp_expires_at, coupon, subtotal_amount, discount_amount, final_amount, logistics_tier or logistics_lane.

Why it matters

If the customer app's migrations have been applied to the production database, every dispatch query in the vendor app raises ProgrammingError: column does not exist — the dispatch engine is dead. If they have not been applied, the customer app is running against a schema its own migration history says it doesn't have. Either way this is a live production hazard, and the type mismatch on coordinates means rounding differences in distance maths between the two apps.

How mature platforms do it

A table has exactly one owning service. Other services read it through an API or a read replica with an explicit, versioned view — never a second ORM model that can silently disagree about the columns.

What to change
  • Both First: run a schema diff against the live database and reconcile. This is a same-day task, not a roadmap item.
  • Customer Re-add assigned_employee (or the agreed replacement column) in a new migration, and align coordinate column types.
  • Both Then: retire the second ORM definition. The vendor app should reach bookings through the integration API from X-02, keeping only its own workforce_* tables locally.

Evidence: Customer/backend/service_requests/migrations/0038_remove_workforce_models_and_fields.py:73–76 vs vendor/backend/service_requests/models.py:165–170 and workforce_api/services/automatic_dispatch.py:330, 723.

X-05
There is no vendor entity — the "vendor app" is a single company's employee app
P0
What's missing

A technician signing up becomes a User(role="employee") plus an Employee row attached to a Company that defaults to a hard-coded CalServices Operations tenant. There is no partner or vendor business object: no service-provider profile, no fleet, no shop, no crew, no agreement, no coverage area of its own, no independent rating, no ledger. The word "vendor" in the codebase means "employee of the platform's own company".

Why it matters

This is the difference between a workforce-management product and a marketplace. Every marketplace behaviour the brief asks for — vendor reputation, vendor onboarding, vendor payouts, vendor-level quality control, customers seeing who is coming — has no object to hang off. Adding it later means touching the dispatch engine, the payment model, the ratings model and the admin console simultaneously.

How mature platforms do it

Two clearly separated tiers: a partner (the business entity that is onboarded, contracted, rated and paid) and a resource (the individual person or vehicle that executes a job). Home-services platforms match on partner then person; logistics platforms match on person-plus-vehicle. Both keep the partner's commercial record — commission rate, payout account, compliance state — separate from the individual's operational record.

What to change
  • Vendor New app vendor/backend/partners/ with Partner, PartnerAgreement, PartnerServiceArea, PartnerRating; Employee gains a nullable partner FK so today's direct-employed technicians remain valid.
  • Vendor Extend the onboarding wizard (frontend/src/pages/onboarding/OnboardingWizardPage.jsx) with a partner track alongside the individual track.
  • Vendor Move the onboarding state currently buried in Employee.bank_details JSON into real columns — dispatch Gates 2 and 8 read bank_details["onboarding"]["status"] and bank_details["leaves"] from an unindexed JSON blob on every candidate evaluation.
  • Customer Surface partner identity in the booking and tracking payloads (_build_tracking_payload currently hard-codes vendor name to "Sevo").

Evidence: vendor/backend/workforce_api/views.py:143–215 · vendor/backend/employees/models.py:36 · Customer/backend/service_requests/views.py:654.

X-06
No commission, payout or settlement model anywhere
P0
What's missing

Money flows in (booking amount, COD collection) and stops. There is no take-rate, no partner earnings ledger, no payout batch, no reconciliation of cash a technician collected against cash the platform is owed. The only related fields are Package.platform_fee (a flat ₹29 default that is never added to any total) and an employee payroll module (WorkforcePayPeriod, WorkforcePayslip) that models salaried wages, not marketplace earnings.

Why it matters

The platform cannot state its own revenue, cannot pay a partner, and cannot detect a technician who collected cash and did not remit it. At any real volume this is not a feature gap, it is an accounting control failure.

How mature platforms do it

Every completed job writes an immutable earnings entry: gross fare, platform commission, taxes, incentives, adjustments, net payable. Cash-collected jobs write a negative entry against the partner's float. A settlement run nets the entries per partner per cycle and emits one payout instruction. The ledger is append-only and reconciles to the gateway.

What to change
  • Vendor New models PartnerEarning (one row per job, immutable), PartnerLedgerEntry, PayoutBatch in the new partners app.
  • Vendor Write an earning row on the completed transition in service_requests/state_machine.py and on every PaymentCollectionEvent.
  • Customer Apply Package.platform_fee and Package.gst_rate in server-side pricing (see HS-B-02) so the commission base is a real number.
  • Vendor Add a technician-facing earnings screen; EmployeePerformancePage.jsx is the natural home.

Evidence: search for commission|payout|settlement|take_rate across both backends returns one hit — Customer/backend/service_requests/models.py:717.

X-07
Notifications are email-only; there is no SMS, push or WhatsApp channel
P0
What's missing

service_requests/notifications.py is 716 lines of send_mail(...) — every booking confirmation, reschedule, refund, complaint and feedback link goes out as email and nothing else. The one SMS path that exists (OTP login) ships with MockSMSProvider, which prints the code to the server console; a Twilio provider is stubbed but not in requirements.txt. There is no Firebase/FCM dependency in either frontend. The customer web app's only "push" is the browser Notifications API, which does nothing inside the shipped WebView app.

Why it matters

In this market SMS and WhatsApp are the channel — a large share of customers will not have supplied an email at all, and the booking form treats email as optional. Right now a customer who books with a phone number receives no communication of any kind for the entire lifecycle of the job. Technicians receive job offers only as an in-app WorkforceNotification row, visible only if the dashboard tab is open, with a 5-minute offer expiry running against them.

How mature platforms do it

A notification service with one message definition rendered per channel, a per-user channel preference and consent record, delivery receipts, and retry with fallback (push → SMS if unread in N seconds). Transactional SMS goes through a DLT-registered template. Job offers reach a partner as a high-priority push with sound, not a database row.

What to change
  • Both New shared notifications service: Template, Message, DeliveryAttempt, channel adapters for SMS (MSG91/Gupshup/Twilio, DLT templates registered), WhatsApp Business, FCM push and email.
  • Customer Replace direct send_mail calls in notifications.py with notify(event, recipient, context); keep the existing HTML templates as the email renderer.
  • Customer Set a real SMS_PROVIDER and add the SDK to requirements.txt; accounts/services.py:90 already has the provider interface.
  • Vendor Fire push on WorkforceNotification creation, especially JOB_OFFER in automatic_dispatch.py:632.

Evidence: Customer/backend/accounts/services.py:58–94 · Customer/backend/requirements.txt (no twilio, no firebase) · Customer/frontend/package.json (no messaging SDK).

X-08
The mobile app is a WebView shell, and the technician has no app at all
P0
What's missing

SEVO.apk is a Flutter app whose entire job is to load https://customer.caldimservices.online in a WebView. Its pubspec.yaml declares webview_flutter and url_launcher and nothing else — no state management, no HTTP client, no maps, no notifications. A native client with Riverpod, GoRouter, auth/booking/tracking repositories and a Razorpay key exists in git history but is not what ships. Technicians have no app; they run the React workspace in a mobile browser.

Why it matters

A WebView cannot do the four things these categories depend on: background GPS, reliable push, native payment SDKs (UPI intent, Razorpay checkout), and camera/storage permissions that survive a backgrounded app. Concretely: the moment a technician locks their phone, GPS transmission stops, and 120 seconds later the dispatch engine classifies them as stale and stops offering them work — while the customer's tracking map freezes.

How mature platforms do it

Both sides are native or Flutter-native. The partner app in particular is built around a foreground service with a persistent notification, exactly so location keeps flowing with the screen off — this is not optional for any category that promises live tracking.

What to change
  • Customer Restore the native Flutter client from history (lib/core/network, lib/features/* at commit 216390e~), add dio, flutter_riverpod, go_router, firebase_messaging, google_maps_flutter, razorpay_flutter, and finish the screens the router already declares.
  • Vendor New technician mobile app — this is a build, not a port. Minimum: login, online/offline toggle, job offer with sound + accept/decline countdown, navigation, arrival + OTP, proof capture, cash collection, earnings.
  • Vendor Background location via a foreground service; keep the 25-second heartbeat cadence useGPSPosition.js already uses so MAX_GPS_AGE_SECONDS = 120 stays satisfiable.

Evidence: Customer/Mobile App/calservices_customer — lib/main.dart and pubspec.yaml at HEAD · vendor/frontend/src/hooks/useGPSPosition.js:27 vs automatic_dispatch.py:34.

X-09
No customer-to-technician channel, and the technician's real phone number is exposed
P1
What's missing

There is no in-app chat, no call button, no number masking. The tracking payload ships technician_phone as a raw personal number to any client that has the tracking token. There are canned-message and communication-log models in customer_care, but they serve support tickets, not the customer↔technician relationship.

Why it matters

"Where are you", "the gate code is 4102", "I'll be ten minutes late" is the highest-volume interaction in both categories, and today it happens on personal numbers outside the platform — which means no record when something is disputed, no protection for the technician after the job ends, and every off-platform conversation is an opportunity to take the next job off-platform too.

How mature platforms do it

In-app chat with quick replies for the common messages, plus a masked-call bridge (Exotel, Knowlarity, Twilio proxy) that connects the two parties through a platform number that expires when the job closes. Both are logged and both are available to support during a dispute.

What to change
  • Both New JobMessage model scoped to a booking, delivered over the existing customer WebSocket and the vendor SSE stream.
  • Both Integrate a call-masking provider; replace technician_phone in the tracking payload with a session-scoped masked number.
  • Customer service_requests/views.py:_build_tracking_payload — stop returning the raw number even when has_full_access is true.

Evidence: no chat, masked, exotel or equivalent in either backend · Customer/backend/service_requests/views.py:683–697.

X-10
Two different mapping stacks produce two different ETAs
P1
What's missing

The customer app draws routes with Leaflet and fetches geometry from public OSRM demo servers (router.project-osrm.org, routing.openstreetmap.de). The vendor app loads the Google Maps JS API and uses DirectionsService. Neither ETA is computed server-side; each client calculates its own, from a different engine, with different traffic assumptions — and the dispatch engine ranks candidates on straight-line haversine distance, a third measure again.

Why it matters

The customer is told 14 minutes, the technician's app says 22, and dispatch picked that technician because they were 3 km away as the crow flies across a river with no bridge. ETA credibility is the main thing a tracking screen sells; two engines guarantee it is wrong for one of the two parties. The public OSRM demo servers are also rate-limited and explicitly not licensed for production traffic.

How mature platforms do it

One routing provider, called server-side, cached, and broadcast to both parties as a single authoritative ETA. Dispatch ranks on road-network travel time, not straight-line distance — the difference decides who gets the job.

What to change
  • Both New server-side routing service (self-hosted OSRM, Google Routes, or Mapbox) exposing eta(origin, destination, mode); both clients render the ETA they are given rather than computing one.
  • Vendor automatic_dispatch.py:get_eligible_candidates — replace proximity_score = 100 - dist_km*2 with a travel-time score from a batched distance-matrix call over the top N haversine candidates.
  • Customer Retire frontend/src/api/routing.js's public-server fallback list.

Evidence: Customer/frontend/src/api/routing.js:7–12 · vendor/frontend/src/utils/loadGoogleMaps.js · vendor/backend/workforce_api/services/automatic_dispatch.py:466–476.

X-11
Dispatch is an unsupervised polling loop, not a service
P1
What's missing

Matching runs as python manage.py dispatch_pending_workforce_jobs --loop --interval 5 — a single process, no supervisor, no health endpoint, no lock preventing two copies, no alerting if it dies. Celery and django-celery-beat are installed in the customer app and unused for this. There are no metrics on the dispatch funnel: how many bookings went unmatched, median time to accept, offer decline rate per technician.

Why it matters

If this process stops, no booking is ever assigned and nothing alerts anyone — the failure mode is silence. And without funnel metrics there is no way to answer the only question that matters operationally: why did this booking not get a technician? The engine logs richly to stdout (9GATE_RESULT, DISPATCH_REJECT) but nothing aggregates it.

How mature platforms do it

Matching is event-driven — a new booking enqueues a match task immediately, and a periodic sweeper only catches strays. Every rejection reason is a counter on a dashboard, with alerts on unmatched-rate and time-to-assign.

What to change
  • Vendor Move dispatch_pending_jobs onto Celery: an immediate task on booking creation, a beat sweeper every 30 s for expired offers, and a distributed lock so concurrent workers cannot double-offer.
  • Vendor Persist the gate results already computed in check_candidate_eligibility to a DispatchAttempt table so "why unmatched" is queryable, not grep-able.
  • Vendor Add /healthz and export counters for offers created, accepted, expired, and bookings unassigned > 10 min.

Evidence: vendor/backend/workforce_api/management/commands/dispatch_pending_workforce_jobs.py · Customer/backend/quicktims/celery.py (configured, unused for dispatch).

Part 2

Home Services — measured against NoBroker

The defining property of this category is that the job is scheduled, the scope is uncertain, and the customer is letting a stranger into their home. Everything the reference platform does follows from those three facts: appointment slots with real capacity, an inspect-then-quote loop for uncertain scope, and heavy investment in trust signals before the technician arrives.

Registration, authentication & trust

Six gaps. The customer side has a decent OTP mechanism that nothing real is wired into; the technician side has a thorough document-verification workflow with no identity verification underneath it.

HS-A-01
Customer OTP login prints the code to the server console
P0
What's missing

The OTP mechanism itself is sound — hashed codes in OTPRequest, expiry, attempt limits, IP and identifier rate limiting, an audit log, a pluggable provider interface. What is missing is a provider. get_sms_provider() returns MockSMSProvider unless SMS_PROVIDER=twilio, and the Twilio SDK is not in requirements.txt. Email OTP goes through send_mail, so it works only if SMTP is configured and only for customers who gave an email.

Why it matters

Nobody can log in. This is the first screen of the product.

How mature platforms do it

Phone-first OTP over a DLT-registered transactional SMS template, with auto-read on Android via the SMS Retriever API, a resend timer, and a truecaller/one-tap alternative. Email is the fallback, not the primary.

What to change
  • Customer Add an MSG91 or Gupshup provider class beside TwilioSMSProvider in accounts/services.py, register the DLT template, set SMS_PROVIDER.
  • Customer Add the SDK to requirements.txt and the credentials to deployment config; MockSMSProvider should be selectable only when DEBUG is true.
  • Customer Emit the SMS from a Celery task — request_otp currently calls the provider inline.

Evidence: Customer/backend/accounts/services.py:58–94, 226–227.

HS-A-02
Booking is fully anonymous and silently creates a shadow account
P1
What's missing

BookingCreateView is AllowAny. If the phone number doesn't match an existing user it creates one — username = cust_<phone>, no password, no verification — and attaches the booking to it. The phone number is never proved to belong to the person booking.

Why it matters

Anyone can create bookings against anyone's phone number, which is both a spam vector and a way to poison a real customer's history: the next time that person logs in with OTP they inherit bookings they never made. It also means the platform's customer count is fiction — a mix of real accounts and booking-form artefacts.

How mature platforms do it

Browse and price without an account; the moment the booking is confirmed, verify the phone with an OTP inline in the checkout sheet. The account is created from a verified number, not from a typed one.

What to change
  • Customer Require a verified-phone token on POST /api/booking/ — issue a short-lived signed token from CustomerOTPVerifyAPIView and validate it in BookingCreateView.
  • Customer CustomerEntryFlowModal.jsx already implements the OTP sheet; move it in front of checkout submission rather than beside it.
  • Customer Mark auto-created users is_verified=False and exclude them from customer analytics until they complete a verified login.

Evidence: Customer/backend/service_requests/views.py:234, 312–347.

HS-A-03
There is no logged-in customer area in the web app
P1
What's missing

Every customer-facing route in App.jsx is public: landing, booking, three logistics pages, a token-scoped feedback page, a token-scoped tracking page. There is no /my-bookings, /profile, /addresses or /payments route. The API supports all of it — /booking/my-bookings/, /auth/customer/profile/, /auth/customer/addresses/ — and the booking page fetches order history inline, but there is no destination a returning customer can navigate to.

Why it matters

Repeat rate is the whole economics of home services. A customer who cannot find their past bookings, saved addresses or invoices without digging up an email link is a customer who re-books from scratch, or doesn't.

How mature platforms do it

An account tab with bookings (upcoming / past), saved addresses, payment methods, invoices, coupons, referrals and support history. "Book again" from a past booking is one tap and pre-fills everything.

What to change
  • Customer Add /account/* routes in ui/routes.js and ui/App.jsx behind a customer guard, reusing CustomerLayout.jsx.
  • Customer New pages: MyBookingsPage, SavedAddressesPage, InvoicesPage — all three back onto existing endpoints.
  • Customer Add "Book again" that rehydrates cart_data from a past ServiceRequest.

Evidence: Customer/frontend/src/ui/App.jsx:298–351 · Customer/backend/accounts/urls.py:52–61.

HS-A-04
Technician signup verifies neither phone nor email nor identity
P0
What's missing

WorkforceSignupView takes an email, a mobile number and a password and creates an active account. No OTP on either channel. The onboarding wizard that follows collects documents and an admin verifies them, but there is no government-ID check, no police verification record, no address proof requirement in the model, and no background-check status field. Registration & authentication

GT-A-01
There is no vehicle — a driver is a technician with a job title
P0
What's missing

The Employee model has no vehicle at all: no type, no registration number, no capacity in kg or cubic feet, no body dimensions, no fuel type, no permit class, no ownership record. The logistics.ServiceTier catalog describes vehicle classes to the customer (3-wheeler, Tata Ace, 2-wheeler, with capacity labels), but nothing on the supply side says which driver can actually provide one.

GT-A-02

Booking, fare estimation & matching

GT-B-01
There is no fare engine — only flat lane prices and "starting from" tiers
P0
What's missing

resolve_logistics_fare() returns the Lane.fare if a pre-agreed route was chosen, otherwise the ServiceTier.starting_price, otherwise whatever the client submitted. There is no base fare plus per-kilometre rate, no minimum distance, no waiting charge, no loading/unloading labour charge, no toll or parking pass-through, no night or peak multiplier, no surge, and no return-trip pricing.

Why it matters

The platform cannot price a route it has not pre-agreed, which means it can only serve a fixed list of popular lanes out of Hosur. Anything else falls through to the client's number. It also means a 4 km job and a 40 km job on the same tier are quoted identically.

How mature platforms do it

Fare = base + (distance × per-km rate) + (loaded time × per-minute rate) + waiting beyond free minutes + labour + tolls + surge, per vehicle class, per city, versioned so historic bookings reprice consistently. The estimate is shown before booking; the actual is computed from the trip that happened.

What to change
  • Customer New FareRule model per vehicle class × city with all the components above, versioned by effective date. Lane stays as an override for pre-agreed routes.
  • Customer New fare_service.estimate(tier, pickup, drops, options) using the server-side routing distance from X-10; expose it as a pre-booking quote endpoint.
  • Customer Replace resolve_logistics_fare's trust-the-client fallback with a hard rejection.
  • Customer Persist the estimate and the fare-rule version on the booking so the final fare in GT-C-01 is auditable against it.

Evidence: Customer/backend/service_requests/services/logistics_pricing.py:26–50 · Customer/backend/logistics/models.py:104–133.

GT-B-02
A five-minute sequential offer is unusable for on-demand transport
P0
What's missing

The same dispatch path serves both categories: one offer, one candidate, DEFAULT_OFFER_DURATION_MINUTES = 5, then the next candidate. A customer standing beside their goods waits five minutes per decline. There is also no "book now" concept — preferred_date is a required field on every booking.

Why it matters

This is the single behaviour that most separates the product from Porter. On-demand transport is judged on time-to-match; two declines here is a ten-minute wait during which the customer opens a competitor. The batching work in HS-B-05 is optional for home services and mandatory here.

GT-B-03
The job lifecycle has no trip states
P0
What's missing

The vendor state machine runs accepted → on_the_way → arrived → service_started → in_progress → proof_submitted → completed. Payment & transaction handling

GT-C-01
No final fare — the estimate is the invoice
P0
What's missing

Whatever total_amount was set at booking is what gets collected. The trip is measured as it happens. At the drop, the actual fare is computed, shown to both parties with each component itemised, and collected. A capped variance against the estimate protects the customer; anything beyond it requires explicit approval.

Why it matters

This is the category's core control. Without it the platform cannot prove the goods were handed to the right person, cannot resolve a "never arrived" dispute, and has no document a business customer can file. The pieces to build it — hashed OTP with expiry and attempt limits, geofenced position capture, photo upload — all already exist in the vendor app for other purposes.

How mature platforms do it

At the drop the driver captures recipient name and a signature or an OTP sent to the consignee, plus a photo of the delivered goods and the captured GPS position. A delivery receipt goes to both sender and receiver.

What to change
  • Vendor New DeliveryProof model per drop stop: recipient name, relationship, signature image, OTP hash and verification timestamp, photo, captured lat/lng, condition note.
  • Vendor Reuse the OTP pattern from JobPayment.payment_confirmation_otp_hash, which is already hashed with expiry and attempt limits.
  • Customer Send the delivery OTP to the consignee from GT-A-03; emit a delivery receipt to both parties.
  • Both Block the delivered transition until proof exists, the same way arrived is already gated on the geofence check.

Evidence: vendor/backend/workforce_api/models.py:741–765 · models.py:1200–1215 (the OTP pattern to reuse).

GT-D-02
One ETA where the trip has two legs, and no trip replay
P1
What's missing

The tracking payload computes a single distance and ETA from the technician to the booking's coordinates — the pickup. There is no ETA to the drop, no progress along the loaded leg, no distance remaining, and no completed-trip path. JobLocationPoint stores the breadcrumb trail on the vendor side and it is never exposed.

Why it matters

Once the goods are loaded, the customer's only question is when they arrive at the destination — and that is precisely the number the tracking screen cannot show. The stored breadcrumbs would also settle route disputes and support distance-based billing, at no additional collection cost.

How mature platforms do it

ETA is phase-aware: to pickup before loading, to the next stop after. The trip line is drawn as it happens and retained, so both parties can replay the route afterwards.

What to change
  • Customer Make _build_tracking_payload compute ETA to the current target stop rather than always to the booking address.
  • Vendor Expose a trip-path endpoint over JobLocationPoint, decimated for transfer; emit the path with the completion event.
  • Customer Draw the loaded leg and remaining distance on CustomerTrackingMap.jsx.

Evidence: Customer/backend/service_requests/views.py:616–617, 671–678 · vendor/backend/workforce_api/models.py:1061–1092.

GT-D-03
The person receiving the goods is never told anything
P1
What's missing

All notifications and the tracking link go to the booking customer. The consignee — who does not exist as a record (GT-A-03) — receives no dispatch notice, no arrival warning, no tracking link and no delivery confirmation.

Why it matters

In most transport bookings the sender and the receiver are different people in different places. A receiver who does not know a vehicle is coming is a failed delivery, and the sender ends up relaying every update by phone.

How mature platforms do it

The receiver gets their own tracking link and their own notification stream — dispatched, out for delivery, arriving, delivered — scoped so they see only what concerns their stop.

What to change
  • Customer Issue a per-stop tracking token alongside the booking-level one; the tracking_token mechanism and the public tracking view already support token-scoped access.
  • Customer Add consignee recipients to the milestone map in HS-D-06, scoped to their stop.

Evidence: Customer/backend/service_requests/models.py:266 (single booking-level token) · views.py:920–955.

Ratings & partner management

GT-E-01
Feedback asks home-services questions about a delivery
P1
What's missing

ServiceFeedback collects a rating, employee_behaviour, work_quality and issue_resolved. None of those describe a trip. There is no punctuality dimension, no goods-condition dimension, no vehicle-condition rating, no handling or packing quality, and no per-form variation by category.

Why it matters

"Was your issue resolved?" is meaningless after a house move, so the answers are noise — which means the transport side of the marketplace has no usable quality data at all, and the scorecard in HS-E-05 has nothing to score it on.

How mature platforms do it

The rating form varies by category. Transport asks about punctuality, goods condition, driver conduct and vehicle condition, with quick-tap tags rather than free text.

What to change
  • Customer Replace the fixed columns on ServiceFeedback with a category-scoped question set plus a JSON answer map; keep the headline rating as a column.
  • Customer Add a transport question set and render it in FeedbackPage.jsx and the in-app sheet from HS-E-02.

Evidence: Customer/backend/service_requests/models.py:591–617.

GT-E-02
Declining and cancelling carry no consequence
P1
What's missing

WorkforceJobOffer records REJECTED, EXPIRED and CANCELLED per offer, and the technician can cancel an accepted assignment. Nothing aggregates any of it. There is no acceptance rate, no cancellation rate, no cancel-after-accept penalty, and none of it affects who gets offered the next job.

Why it matters

In on-demand transport, cherry-picking is the dominant supply-side failure — accept, see the destination, cancel. Without a measured and enforced acceptance and cancellation rate, the drivers who behave worst are indistinguishable from those who behave best, and short or awkward trips never get served.

How mature platforms do it

Acceptance rate and cancellation rate are published to the partner, feed dispatch priority, and gate incentives. Cancelling after accepting costs more than declining, and a late cancellation compensates the customer.

What to change
  • Vendor Roll WorkforceJobOffer outcomes into the PartnerScorecard from HS-E-05 as acceptance and cancellation rates over a trailing window.
  • Vendor Weight the dispatch ranking by them, and add a cooldown after a cancel-after-accept in WorkforceJobTechnicianCancelView.
  • Customer Auto-issue a goodwill credit when a driver cancels after acceptance — the wallet from HS-C-07.

Evidence: vendor/backend/workforce_api/models.py:393–426 · services/automatic_dispatch.py:466–492.

Part 4

Edge cases & error handling

Nine defects that are not workflow gaps but will produce incidents. Three of them are security issues that should be fixed before anything else in this document.

EC-01
The service-start OTP is derivable by the person it is meant to check
P0
What's missing

ServiceRequest.save() generates start_otp as sha256("calservices_booking_otp_{request_id}_{phone}_{customer_name}"), taking the first eight hex digits modulo 900000. Every input is known to the technician, and the salt is a literal in the source. The value is stored in plaintext on the row and compared with str(entered) == str(sr.start_otp). An otp_hash column exists and is not used on this path.

Why it matters

The OTP exists so that work cannot be marked started without the customer present. A technician who can compute it can start and complete a job they never attended — and in the COD flow, trigger collection. The control provides no assurance at all.

How mature platforms do it

A random code generated server-side at the moment it is needed, delivered to the customer over a channel the partner cannot read, stored only as a hash, single-use, short-lived, rate-limited.

What to change
  • Customer Generate the code with secrets.randbelow at the arrived transition, not at booking creation; store only the hash in otp_hash and set otp_expires_at.
  • Customer Deliver it to the customer by SMS or push, and remove start_otp from every serializer and tracking payload.
  • Customer Stop sending start_otp in the dispatch payload in workforce_integration/services.py:92.

Evidence: Customer/backend/service_requests/models.py:347–350 · views.py:2285.

EC-02
OTP verification is unauthenticated and bypasses the state machine
P0
What's missing

BookingVerifyStartOTPView is AllowAny, identifies the booking by a guessable sequential id or request id, and on success writes sr.status = "in_progress" directly rather than calling apply_transition. A booking sitting in confirmed jumps straight to in_progress without ever passing acceptance, travel, or the geofenced arrival check the vendor state machine enforces.

Why it matters

It defeats the arrival gate that the vendor app is careful about, and it is callable by anyone. Combined with EC-01, the OTP control is bypassable end to end.

How mature platforms do it

Verification is authenticated as the assigned partner, on a job that is already in the arrived state, and every write goes through the one transition function.

What to change
  • Customer Require the assigned technician's credential (or the service credential from X-02); reject unless the booking is in arrived.
  • Customer Route the write through apply_transition — the direct assignment at views.py:2288 is the bug.
  • Customer Audit all direct sr.status = ... assignments in views.py for the same pattern.

Evidence: Customer/backend/service_requests/views.py:2258, 2285–2293.

EC-03
Booking creation is not idempotent
P1
What's missing

POST /api/booking/ takes no idempotency key. A double-tap, a retry on a slow response, or a network retry creates a second booking, a second coupon redemption and a second dispatch. The webhook receiver on the same codebase does implement idempotency properly — the booking endpoint does not.

Why it matters

Duplicate bookings are the most common support ticket in this class of product, and they are worse here because the booking POST can block for up to five seconds (X-02), which makes users tap again.

How mature platforms do it

The client generates an idempotency key per checkout attempt; the server stores it against the created order and returns the same order for any repeat.

What to change
  • Customer Accept an Idempotency-Key header, store it uniquely against the booking, return the existing booking on repeat.
  • Customer Apply the same to /payment/verify/ and /customer/refunds/create/.

Evidence: Customer/backend/service_requests/views.py:229–430 vs workforce_integration/views.py:100–130.

EC-04
Human-readable booking IDs are generated with a race condition
P1
What's missing

_generate_request_id() reads the highest existing row for a category prefix, adds one, then loops while the candidate exists. There is no lock and no unique sequence. Two concurrent bookings in the same category can compute the same candidate, and the retry loop is a read-then-write with the same race.

Why it matters

request_id is unique at the database level, so the loser gets an IntegrityError — a failed booking after payment, under exactly the load conditions where it is most expensive. The function is also O(n) on every booking.

How mature platforms do it

A database sequence per prefix, or a random collision-resistant identifier. Never a read-max-and-increment.

What to change
  • Customer Replace with a Postgres sequence per category prefix, or a counter row locked with select_for_update.
  • Customer Move ID assignment out of save() into the creation service so it participates in the booking transaction explicitly.

Evidence: Customer/backend/service_requests/models.py:51–76.

EC-05
Failures are swallowed and reported as success
P1
What's missing

The integration client returns {"success": True, "fallback": True} when a call fails. Notification helpers use fail_silently=True inside bare excepts. Tracking broadcasts log a warning and continue. There is no dead-letter queue, no retry, and no alert — the system's default response to a failed cross-service operation is to pretend it worked.

Why it matters

It is why the integration in X-02 could be entirely non-functional without anyone noticing. Every silent fallback removes a signal that something needs fixing.

How mature platforms do it

Failures are recorded, retried with backoff, and escalated to a dead-letter queue with an alert. A degraded path is an explicit state, never a success return.

What to change
  • Customer Return honest failure states from WorkforceIntegrationService; put every cross-service call on a Celery task with retry and a DLQ table.
  • Both Add error tracking (Sentry or equivalent) — neither backend has any.
  • Both Alert on DLQ depth and on integration failure rate.

Evidence: Customer/backend/workforce_integration/services.py:131–135, 286–290 · service_requests/notifications.py.

EC-06
Rate limiting is one blunt global rule, and the vendor app has none
P1
What's missing

The customer app does configure DRF throttling — 60 requests per minute anonymous, 300 authenticated, globally. What is missing is any differentiation: booking creation, payment verify, tracking-token lookup, feedback submission and coupon validation all share the same 60/minute allowance as browsing the catalog, and there are no scoped throttles for the sensitive writes. The two OTP views in accounts/views.py explicitly set throttle_classes = [], relying entirely on the in-service limiter. The vendor app configures no throttling at all.

Why it matters

60 attempts a minute against a tracking-token lookup or an unauthenticated payment-verify endpoint is a lot of attempts. The global rule is sized for protecting the database from load, not for protecting a specific endpoint from abuse — and the vendor app, which exposes signup, login and the SSE stream, has no ceiling at all.

How mature platforms do it

Tight per-endpoint scopes on unauthenticated writes on top of a generous global rule, plus a WAF or bot-management layer in front, plus a challenge on the anonymous booking form.

What to change
  • Customer Add ScopedRateThrottle scopes for booking creation, payment initiate/verify, tracking lookup, feedback and coupon validation — single-digit rates per minute per IP.
  • Vendor Configure DEFAULT_THROTTLE_CLASSES and rates in workforce_core/settings.py; scope signup and login tightly.
  • Customer Add a challenge to anonymous booking submission.

Evidence: Customer/backend/quicktims/settings.py:243–251 · accounts/views.py:982, 1114 · vendor/backend/workforce_core/settings.py:158–168 (no throttle keys).

EC-07
No test coverage on the paths that were changed most recently
P1
What's missing

There are substantial test suites — spatial dispatch, offer expiry and rings, GPS geofence auto-clock-in, registration routing — sitting loose in the repository root as scripts rather than in a runner. What is not covered: the pricing path, the payment path, the state-machine divergence between the two apps, and the integration contract. There is no CI test job in either .github/workflows.

Why it matters

The two highest-risk gaps in this document — client-set prices and unauthenticated payment confirmation — are exactly the kind that a single contract test would have caught, and would catch again if reintroduced.

How mature platforms do it

Contract tests between services run in CI on both repositories. Pricing and payment have property-based tests. A schema-drift check runs against the shared database on every migration.

What to change
  • Both Move the existing suites under tests/ and add a CI job that runs them.
  • Both Add contract tests for the webhook event set and the shared status enum (see X-01, X-03).
  • Customer Add tests asserting that a client-supplied total_amount is ignored and that payment verification fails without a valid signature.

Evidence: Calservices/backend/test_*.py (loose scripts) · no test step in either workflow directory.

EC-08
Tracking tokens never expire
P2
What's missing

tracking_token is a UUID4 minted at booking creation, never rotated and never expired. It authorises the public tracking view, the live-location endpoint and, in some paths, cancellation. Anyone who ever held the link — forwarded, in a browser history, in a screenshot — retains access to the booking's address, technician identity and phone number indefinitely.

Why it matters

The token is doing real authorisation work over personal data, so its lifetime should match the job's. It currently outlives it by forever.

How mature platforms do it

Share links are scoped to the trip and expire shortly after it ends; sensitive fields drop out of the payload once the job closes.

What to change
  • Customer Add tracking_token_expires_at, set to completion plus a short window; check it in CustomerPublicTrackingView and the live-location view.
  • Customer Redact technician phone and address from the payload once the booking is terminal.

Evidence: Customer/backend/service_requests/models.py:266, 351–353 · views.py:920–955.

EC-09
Anyone can download any customer's invoice
P0
What's missing

InvoiceDownloadView is permission_classes = [AllowAny] and resolves the booking from a sequential integer id or a predictable request id like AC0012. There is no ownership check and no token requirement. The PDF it returns prints the customer's name, phone, email and full service address, plus the amount and transaction id.

Why it matters

Iterating /api/booking/1/invoice/ upward enumerates the entire customer base's contact details and home addresses. This is a direct personal-data breach, not a theoretical one, and the identifiers are guessable by design because they are meant to be human-readable.

How mature platforms do it

An invoice is served only to the authenticated owner or against a signed, expiring link. Documents containing personal data are never addressable by a sequential identifier alone.

What to change
  • Customer Require an authenticated owner, an admin, or a valid tracking_token in InvoiceDownloadView; the ownership check in CustomerBookingCancelView is the pattern to reuse.
  • Customer Audit every other AllowAny view in service_requests/ that resolves a booking by id — CustomerBookingLiveLocationView and BookingVerifyStartOTPView are in the same shape.
  • Customer Serve documents through short-lived signed URLs rather than direct id lookup.

Evidence: Customer/backend/service_requests/payment_views.py:171–199, 257–268.
