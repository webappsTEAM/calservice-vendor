**No migration has been applied to any database.** This environment has no route to the live Postgres host, which is stated plainly rather than worked around.

| Migration | Contents | Risk |
|---|---|---|
| Customer `0063` | pre-existing merge node, zero operations | none |
| Customer `0064` | drops legacy add-on/technician-snapshot fields | **destructive — read its header before applying** |
| Customer `0065` | `drop_latitude`, `drop_longitude` | additive |
| Customer `0066` | `fare_breakdown` | additive |

| Vendor `0022` | drops a superseded legacy quote system | **destructive — read its header** |

**Two operations were deliberately excluded and documented rather than applied:**

1. **`Addon.package`** (nullable/SET_NULL → non-nullable/CASCADE) — excluded five times. It would fail against any database holding an `Addon` row with `package_id IS NULL`, and there is no way to check that from here. **Needs `SELECT count(*) FROM service_requests_addon WHERE package_id IS NULL` against the real DB.** `makemigrations --check` will keep reporting it as pending until then — that is expected, not an oversight.
2. **`unique_active_job_offer_per_employee`** — I traced `automatic_dispatch.py` in full and this DB constraint is currently the *only* thing preventing two concurrent `dispatch_job()` calls from double-offering the same technician. Dropping it needs an application-level guard first.

## 5. Google Maps routing status

`get_route_eta()` calls the **Distance Matrix API** using a backend-only `GOOGLE_MAPS_API_KEY` — which was already in `.env` but read by no Python code anywhere. Results are cached ~45s through the project's existing cache framework (Redis in production with graceful degradation, locmem locally); no new infrastructure.

On **any** failure — no key, network error, timeout, `REQUEST_DENIED`, `OVER_QUERY_LIMIT`, `ZERO_RESULTS`, malformed response — it falls back to straight-line haversine, and the result always says which was used via `source`. Nothing presents an estimate as if it were a measured route.

**Honest limitation:** the egress proxy here returns 403 for `maps.googleapis.com`, so a *successful* API response has never been observed from this environment — that path is covered by mocked tests only. The **failure** path was exercised for real: several tests trigger genuine network calls that the proxy rejects, and the graceful fallback was confirmed end-to-end. Whether Distance Matrix is enabled on your key is the one thing to check on first deploy.

## 6. Fare engine status

Implements §H.1: `base_fare + chargeable_km × per_km_rate + loading_unloading + additional_stop_charge × (stops − 2)`, × surge, floored at `minimum_fare`.

- Inputs live on `ServiceTier`, because §H.1 scopes rates to the **vehicle class**, which is what `ServiceTier` already is.
- **Opt-in per tier and inert until used.** Every field is nullable or zero-defaulted; with `per_km_rate` unset a tier falls through to the previous flat lookup. **Applying these migrations changes no existing price.** An admin switches one tier over by setting `per_km_rate`.
- Resolution order: distance quote → `Lane.fare` → `ServiceTier.starting_price` → raise. The distance quote outranks a lane fare deliberately: where the trip can actually be measured, the measured fare is the more accurate one.
- **Packers & Movers is deliberately excluded.** §H.2 makes relocation pricing survey/volume/crew-driven. Pricing it by road distance would be *wrong*, not merely incomplete.
- Waiting charges are not in the upfront quote — §H.1 routes deviations through the existing `WorkExtension` approval flow, so that is reused rather than duplicated.
- The client-submitted `total_amount` is still never trusted, verified end-to-end: a booking submitted with `total_amount: 1.00` is stored at the server-computed `530.00`.

## 7. Driver dispatch status

- **Gate 10 — cash float ceiling.** Blocks further *cash* work above a configurable ceiling (default ₹10,000). Scoped to cash-collecting jobs, so a technician over the ceiling can still take prepaid work. It **fails open**, unlike the other nine gates, which fail closed — a financial-risk control should not be able to take dispatch down platform-wide if the payment tables are unreadable. That asymmetry is intentional and commented at the gate.
- **Rapid offer window.** Transport categories get a 20/25/30s ladder that widens as a job burns candidates, plus a thin-pool bonus, clamped to 15–45s. Every other category keeps bit-for-bit identical minute-scale timing. Packers & Movers is excluded — a surveyed relocation is not an on-demand hail.

**Verification limit, stated plainly:** Gate 10's decision logic is unit-tested, but its wiring into the 10-gate engine is *not* driven end-to-end. `Employee` lives in an app that is entirely `managed=False`, so no table exists in any test database and real `Employee` rows cannot be created. What is executably covered is that the real function accepts the new `job` argument and returns a ten-gate result.

## 8. Proof of delivery status

Previously: the vendor app could POST `job.completion_proof_submitted`, and the handler appended the free-text remarks to `ServiceRequest.description`. That was the entire implementation — no photo, no signature, no recipient, no stop link.

Now: `DeliveryProof` records photo, signature, recipient identity, OTP confirmation or a note — one row per kind, linked to a stop when the payload names one, nullable for the ordinary single-drop booking. Technician identity is snapshotted rather than FK'd (this backend deliberately holds no foreign key into the vendor DB). Per-stop `arrived_at`/`completed_at` are advanced by new webhook events, idempotently. `recipient_phone` is never exposed through the API, with a test asserting it appears nowhere in the serialised payload.

**This is the biggest remaining gap: the Customer side now consumes these events, but the vendor/driver app does not yet emit them.** Until it does, legs, stop progress and proofs will stay empty in production.
