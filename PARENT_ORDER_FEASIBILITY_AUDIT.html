ServiceRequest architecture

ServiceRequest exists and is the single master record for every booking of every kind. Customer/backend/service_requests/models.py:225 — "Master record: created by public booking, driven through state machine."

The exact field

Not set. Compare to status, priority, payment_method, payment_status, logistics_leg and request_kind on the same model — every one of those does declare choices=. service_category is the one identity-defining field on the model that doesn't.

So it's exactly the weaker option: service_category = models.CharField(max_length=150) — a bare string, not a strongly-typed field. It is the only categorical identity field on ServiceRequest without choices=.

Characterization: can "totally-not-a-real-category" be saved?

Verdict: Accepted. Reasoned from a full static trace rather than executed against a live database — the audit brief asked not to modify the codebase, and running a Django test against the shared Supabase instance wasn't a risk worth taking for this check. The trace is deterministic enough that inspection settles it:

  • The serializer field has no choices/validators restricting the value (confirmed above).
  • The model field has no choices, no validators=, no DB check constraint.
  • save() only reads service_category to compute request_id's prefix, via _generate_request_id() (models.py:52-70) — and that function is built to never fail on an unrecognized value: CATEGORY_PREFIX_MAP.get(slug_clean) returns None for "totally-not-a-real-category", and the fallback branch derives a 2-letter prefix from the first two words instead (here: "TN", from totally/not). The booking would be saved as e.g. TN0001.
  • No downstream category-comparison site (§03) recognizes it either, so it simply behaves like a generic/standard booking — it does not error, and it does not get routed into any category-specific business rule (no consultation gate, no advance-payment gate, no structural clearance).

04

Existing AC / Painting / Mason workflows

Traced as they exist. No rewrite is proposed for any of them — none of what follows is a blocker, only a description.

AC

Customer → Booking → ServiceRequest (request_kind="standard") → BookingAssignment → technician → status machine → COMPLETED

Category identified by a bare string at intake, classified nowhere as painting/mason, so it never enters the consultation/quote branch. No category-string-keyed payment gate exists for AC — the generic ALLOWED_TRANSITIONS / STATUS_COMBINATION_RULES tables in state_machine.py enforce payment-status preconditions for every category uniformly.

Painting

Customer → Booking → ServiceRequest (classified is_painting_booking=True at intake, views.py:551) → technician inspects → WorkforceQuote (vendor app) + WorkforcePaintingQuote (1:1 detail) → customer decision (signed decision_token, no login) → SEVO admin approval → CONVERTED → new ServiceRequest(request_kind="quoted_work", parent_request=original) → Payment (advance, per policy) → Work → Completion → WorkforceInvoice

One correction to the brief's assumed flow: a dedicated request_kind="inspection" value is declared in the choices tuple (models.py:465-468), but no code path in this pass was found that ever sets it — the original booking stays request_kind="standard" and is identified as "the inspection job" only by being the target of WorkforceQuote.job. The "quoted_work" kind, by contrast, is genuinely used, for the converted work booking. Worth flagging as either dead code (the inspection choice) or an incomplete wiring — not asserted as a blocker either way.

Mason

Same shape as Painting, with two Mason-specific gates layered on top, both traced precisely:

  • Structural clearance — driven entirely by WorkforceQuote.structural_impact (a field set explicitly when the quote is created), not by the category string at all. requires_structural_clearance / is_structurally_cleared (vendor/workforce_api/models.py, on WorkforceQuote) never reference service_category. This gate cannot be bypassed by a category typo, because it doesn't consult the category in the first place.
  • Advance-payment requirement — this is the one that can be affected by category spelling, and it exists in two independent, inconsistent implementations:
    • Vendor app (workforce_api/services/pricing_policy.py): case-insensitive, DB-driven, fails safe — an unmatched category defaults to DEFAULT_POLICY (100% advance, admin approval on), which is more conservative than Masonry's configured 50%, not less.
    • Customer app (state_machine.py:157-182, inside apply_transition()): case-sensitive, hardcoded ["mason","masonry"], and — critically — fails open: 
      Customer/backend/service_requests/state_machine.py:157-163if service_request.request_kind == "quoted_work" and new_status not in [S.CONFIRMED, S.REJECTED, S.CANCELLED]:
    is_mason = (
        service_request.service_category in ["mason", "masonry"] or
        (service_request.parent_request and service_request.parent_request.service_category in ["mason", "masonry"])
    )
    if is_mason:
        # ...checks Payment.objects sum against PaintingQuote.advance_amount...
      If is_mason evaluates False — which it will for "Masonry", "MASON", or "masonary" — the entire advance-payment block is skipped, and the transition proceeds with no payment check at all. This is the one place in the audit where a category-string mismatch produces an actual bypass, not just a wrong price.

Direct answer to the brief's question: a mistyped or differently-cased Mason category cannot be used to underpay through the vendor-side pricing policy (it fails toward charging more). It can be used to skip the Customer-app's transition-time advance-payment check entirely, because that check's category match is case-sensitive and un-normalized. Whether this is exploitable in practice depends on whether anything upstream can actually cause service_category to be stored as something other than exactly "mason"/"masonry" — the intake path in §01 shows nothing prevents it.

Payment ownership

This is the load-bearing finding for Parent Order feasibility: payment is not owned by one model. Three independent payment/financial records were confirmed, all keyed off ServiceRequest directly, none linked to each other by FK.

ModelLocationLinked toWhat it tracks
PaymentCustomer/service_requests/models.py:1740ForeignKey(ServiceRequest), one-to-manyRazorpay order/payment id + signature, own status (shares ServiceRequest.PaymentStatus). The customer-facing gateway record.
JobPaymentvendor/workforce_api/models.py:1149OneToOneField(ServiceRequest, related_name="payment_record", unique=True)Its own PaymentMethod/PaymentStatus enums (different values than the Customer app's), online vs. cash-on-service, cash collection by employee, amount_due/amount_paid/amount_received/change_returned.
WorkforceInvoicevendor/workforce_api/models.py:2672ForeignKey(WorkforceQuote, PROTECT) + ForeignKey(ServiceRequest)Its own advance_percent/advance_amount/balance_amount/amount_paid/balance_due, own Status (DRAFT→ISSUED→PARTIALLY_PAID→PAID).

No FK connects these three. The Mason advance-payment gate in §04 sums Payment rows (Customer app) against an amount read from PaintingQuote (also Customer app) — it does not consult JobPayment or WorkforceInvoice (both vendor app) at all. Whether those three stay consistent for a given booking depends on application-level discipline across two codebases with two different Django versions (Customer: Django==6.0.8; Vendor: Django>=4.2,<5.1), not on any database constraint.

Trace: Customer → Booking → Payment → ServiceRequest. Confirmed via payment_views.py: PaymentInitiateView creates a Razorpay order against the amount due on a specific ServiceRequest; PaymentVerifyView is explicitly documented (its own docstring) as amount-checked, ownership-checked, HMAC-signature-verified when a live gateway is configured, and idempotent — "a Payment row can only be consumed once (idempotent on repeat calls)."

No recommendation is made here about moving payment ownership — only reporting that it is currently split three ways, each anchored to ServiceRequest, with no shared parent record above it today.

07

Cart / checkout architecture

Confirmed by direct search: no Cart, CartItem, Order, ParentOrder, or OrderItem model exists anywhere in either backend — searched across service_requests, companies, common, inventory, logistics (Customer app) and workforce_api, service_requests, companies, employees (Vendor app). Zero matches in every case.

Customer ↓ "cart" (frontend-only React state; router-passed, never persisted server-side pre-checkout) ↓ Checkout (same generic flow for every category, including Vegetables) ↓ ServiceRequest.cart_data # JSONField(list) — line items with no package_id/addon_id back-reference ↓ Payment (ForeignKey to the same ServiceRequest)
  • Does a cart exist? Only as client-side state, passed through React Router's navigation state into the checkout page. No server-side cart resource, no persistence before submission.
  • Is checkout service-specific? No — one generic checkout flow (routes.booking_checkout) handles AC, Painting, Mason, Logistics, and Vegetables alike.
  • Does checkout create ServiceRequest directly? Yes, one row, synchronously, on submit.
  • Does checkout create Payment directly? Yes, via the flow in §06, against that one ServiceRequest.
  • Cart data: relational or JSON? JSON — ServiceRequest.cart_data = models.JSONField(default=list). Its own code comments confirm items "don't carry a package_id/addon_id back" to the catalog.
  • Can a cart contain multiple services today? Structurally, cart_data is a list and could hold heterogeneous line items, but every booking still resolves to exactly one ServiceRequest with exactly one service_category — there is no code path that splits one cart into multiple ServiceRequest rows of different categories today.
  • Does an Order concept already exist? No, in name or in structure — see §08.
08

Parent Order feasibility

No Order/ParentOrder/OrderItem exists today (§07). But the codebase does already have one real, working precedent for exactly this shape of relationship — just scoped narrowly:

Customer/backend/service_requests/models.py:464-467 — on ServiceRequest itselfparent_request = models.ForeignKey("self", on_delete=models.SET_NULL,
                                   null=True, blank=True,
                                   related_name="child_requests")
request_kind   = models.CharField(max_length=30, default="standard", db_index=True,
                                  choices=[("standard", "Standard"),
                                           ("inspection", "Inspection"),
                                           ("quoted_work", "Quoted Work")])

This self-referential FK is actively used (confirmed in views.py, state_machine.py, and tests/test_painting_module.py) to link a Painting/Mason inspection ServiceRequest to the ServiceRequest(request_kind="quoted_work") created when its quote converts. It is a genuine parent→child pattern already living on the model the brief is asking about — evidence that "one commercial event produces more than one ServiceRequest row, linked together" is not a foreign idea to this codebase. It is, however, one parent → one child in every usage found, and same-model self-reference rather than a distinct commerce-layer entity.

Would this relationship be possible?

Order └── OrderItem └── ServiceRequest

Structurally: yes, and with less friction than a from-scratch design would suggest, for one specific reason — every payment, quote, and invoice model in §05/§06 already points at ServiceRequest, never at a booking-level concept above it. An Order/OrderItem pair introduced purely as a thin wrapper — OrderItem.service_request = ForeignKey(ServiceRequest), nothing more — would not require touching Payment, WorkforceQuote, JobPayment, or WorkforceInvoice at all, because none of them would need to know the wrapper exists. It would sit strictly above the existing graph, not inside it.

The multi-category version — Order → OrderItem → {AC, Painting, Mason} ServiceRequest in one order — is a different claim: it requires one checkout to create multiple ServiceRequest rows and multiple Payment rows (or one payment split across several), and nothing in §06/§07 shows that split ever happening today. That is the part that needs new logic, not just a new table.

A–D

Architecture & Parent Order verdicts

A. Current architecture, as found

Customer ↓ "Cart" (frontend state only) ↓ Checkout (one generic flow, all categories) ↓ ServiceRequest (service_category: free-text CharField) ├── parent_request self-FK (used today: inspection job ←→ quoted_work job, Painting/Mason only) ├── Payment (Customer app, Razorpay, FK → ServiceRequest) ├── WorkforceQuote (Vendor app, canonical quote, FK → ServiceRequest) │ └── WorkforceInvoice (FK → WorkforceQuote + ServiceRequest) └── JobPayment (Vendor app, OneToOne → ServiceRequest)

B. Category architecture verdict

MEDIUM
Is ServiceRequest.service_category safely managed? No — not today. It is a bare, unconstrained CharField, validated nowhere, backed by four uncoordinated category lists instead of one registry, and at least one of those gaps (the Customer-app Mason advance-payment gate, §04) fails open rather than safe. It is rated Medium rather than Low/Not-Ready because nothing found in this audit is silently losing money in production today — the one open-fail path requires a category string that never occurs through the normal Painting/Mason booking UI, which does classify correctly at intake (§03). The risk is latent, not active.

C. Parent Order verdict

HIGH
Can a Parent Order be introduced above ServiceRequest without rewriting AC, Painting or Mason? Yes, for the constrained 1-Order-to-1-ServiceRequest shape. Evidence: every financial and workflow model in §05/§06 already terminates at ServiceRequest, none of them reach "above" it, and a precedent for parent/child ServiceRequest linking already exists and works in production (§08). Not rated READY only because the admin/reporting surface and the checkout sequencing change are real, if small, additions — not because anything found is a blocker.

D. Parent Order proposed placement

Customer ↓ Cart ↓ Checkout ↓ Parent Order (new, thin: id, customer, created_at, status) ├── OrderItem → AC ServiceRequest (existing workflow, byte-for-byte unchanged) ├── OrderItem → Painting ServiceRequest (existing workflow, byte-for-byte unchanged) └── OrderItem → Mason ServiceRequest (existing workflow, byte-for-byte unchanged)

What stays unchanged: ServiceRequest's fields, state machine, parent_request self-FK, every category-comparison site in §03/§04, WorkforceQuote/PaintingQuote/WorkforceInvoice, Payment/JobPayment, the entire Vendor app, and every existing serializer/API/frontend screen. What's new: the Order and OrderItem tables, one additive FK, and whatever checkout-sequencing change is needed to create the Order first.

▸

Grocery / Daily Essentials architecture fit

Evaluated against the actual code above, not against the target diagram in isolation.

Can service_category = "grocery" work without a separate ServiceRequest subclass?

Yes, structurally trivially — §01 already showed service_category accepts any string up to 150 characters, so "grocery" requires no schema change at all. The real question is whether anything downstream needs to recognize it, and the answer from §03/§04 is: only if Grocery needs a category-specific gate the way Mason does. Given this audit's own evidence that hardcoded, scattered category lists are already a live source of bugs (the goods_transport incident), a new category should not be added as a fifth hardcoded list — it's the right moment to introduce one shared, normalized category constant/set, even without touching the field's type.

Product model

The existing generic catalog — CatalogCategory → Service → Package → AddOn (confirmed in the companion Vegetables audit, 8 Sep 2026) — already has the exact shape requested: Package.name, base_price/offer_price, image, status (DRAFT/ACTIVE/INACTIVE/ARCHIVED). It is missing only a product_category-style discriminator (Vegetable vs. Rice vs. Dal) and a sku/unit field — both additive columns, not a new model. Reusable as the Product model; no new Product table is architecturally necessary.

Inventory

Not safe today, confirmed by direct inspection. Package has no stock field of any kind. The existing inventory app's InventoryItem (Customer/backend/inventory/models.py) is scoped to internal operational supplies (equipment/PPE/vehicles/tools) for a Workforce company — its Category choices don't include a customer product, and it has no relationship to Package. Reserve/release-on-cancel requires a genuinely new model: a stock ledger keyed to Package, with physical_stock/reserved_stock/available_stock (or an append-only ledger deriving those). This is new, not a repurpose.

Delivery slot / fulfillment policy

No DeliverySlot, DeliveryWindow, or DeliverySchedule model exists anywhere in either backend (not found in this pass's searches of service_requests, logistics, or workforce_api). However, the closest existing precedent for a configurable, per-category policy table is WorkforceServicePricingPolicy (§02/§04) — a real, admin-editable, DB-backed policy row keyed by category. A FulfillmentPolicy model (cutoff_time, delivery_start_time, delivery_end_time, delivery_days, capacity) is architecturally the same shape as that existing table, and could reasonably live beside it rather than be invented from nothing. The Vegetables module's current 12 PM/6-8 PM logic lives only in a frontend utility (vegetableSchedule.js, per the 8 Sep audit) with no server-side enforcement — exactly the gap a FulfillmentPolicy table would close.

Batch fulfillment vs. on-demand dispatch

Confirmed: the existing dispatch pipeline (BookingAssignment, the Vendor app's eligibility/candidate-ranking/job-offer chain) is built for one technician accepting one job on demand. Nothing in it models a picking/packing/dispatch batch. This is a genuinely separate fulfillment mode from anything in the codebase today — it should not be forced through BookingAssignment, and building it as a distinct, simpler status progression on the Grocery ServiceRequest (or on OrderItem, if Parent Order ships first) avoids distorting the technician-dispatch model that AC/Painting/Mason correctly depend on.

Phase 2 multi-vendor: does Phase 1's data model block it later?

No, provided Phase 1 is built the way this audit's evidence points: as a real, separate line-item concept (OrderItem/Product rows), not folded into cart_data JSON the way Vegetables works today. The reason this matters concretely: §07 showed cart_data items don't carry a package_id back to the catalog, which is precisely what makes later per-item vendor allocation, per-item stock reservation, or per-item refunds hard to retrofit. A grocery OrderItem row with a real FK to Product/Package from day one costs nothing extra in Phase 1 and is what makes "add a vendor FK to that same row later" a genuinely additive Phase 2 change rather than a rebuild.

Final verdict

MEDIUM
1. Category architecture. Functions correctly for the categories in active use today, but is unvalidated and scattered across 4 uncoordinated lists with one confirmed historical production bug and one latent open-fail path (Mason). Fix before extending, don't block on it.
HIGH
2. Parent Order. Can be introduced above AC/Painting/Mason without rewriting any of them, for the constrained 1-Order-to-1-ServiceRequest case the brief itself asks to start with. The multi-ServiceRequest case is real future work, correctly deferred.
MEDIUM CHANGES
3. Grocery / Daily Essentials. The category and Product layers fit with minor additions; Cart, Inventory, DeliverySlot, FulfillmentPolicy, and batch fulfillment are genuinely new models — not a rewrite of anything existing, but not a thin layer either.

What can be reused

  • ServiceRequest as the execution record for a Grocery order (one row = one fulfillment run), unchanged.
  • The generic CatalogCategory → Service → Package → AddOn catalog as the Product model, with additive fields.
  • The parent_request self-FK pattern and request_kind enum as prior art for how Parent Order → ServiceRequest linking should look.
  • WorkforceServicePricingPolicy's shape as the template for a new FulfillmentPolicy model.
  • Payment's Razorpay/idempotency pattern, unchanged, for Grocery checkout.

What needs modification

  • Cart: from frontend-only JSON to a relational structure carrying a real Product FK per line — needed regardless of Parent Order, because it's also what blocks per-item refunds and vendor picking lists today (per the 8 Sep Vegetables audit).
  • Category comparison logic: consolidate the 4 scattered lists (§02) into one shared, normalized source before adding a 5th category family.
  • The Customer-app Mason advance-payment gate in state_machine.py: normalize its category comparison to match the vendor app's case-insensitive approach, independent of anything Grocery-related.

What should NOT be changed

  • ServiceRequest's existing fields, state machine, or the AC/Painting/Mason status flows themselves — no architectural blocker was found that requires touching them.
  • WorkforceQuote, PaintingQuote, WorkforceInvoice, Payment, JobPayment — none need to become aware of Order or Grocery for Phase 1.
  • The Vendor app's technician-dispatch pipeline — Grocery's batch fulfillment should be built beside it, not through it.

What should be added

  • Order / OrderItem (thin, 1:1 with ServiceRequest to start).
  • A stock/reservation ledger on Product (physical/reserved/available).
  • FulfillmentPolicy (cutoff, delivery window, days, capacity) — modeled on WorkforceServicePricingPolicy.
  • A batch picking → packing → dispatch status progression, separate from BookingAssignment.
  • One shared, normalized category registry, used by every existing comparison site as it's touched.

What stays Phase 2

  • Multi-vendor allocation and any VendorOrder/vendor-split concept.
  • One Order spanning multiple ServiceRequests of different categories in a single checkout/payment.

Recommended sequence

Preserve existing AC/Painting/Mason (change nothing) → introduce the thin 1:1 Parent Order → build the generic Grocery/Daily-Essentials foundation (Product fields, stock ledger, FulfillmentPolicy) → implement Vegetables as Phase 1 on top of that foundation, replacing its current JSON-cart implementation rather than extending it further.
